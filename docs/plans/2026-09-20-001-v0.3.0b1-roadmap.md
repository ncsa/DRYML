# DRYML 0.3.0b1 Roadmap

## Release Goal

Deliver a usable ML-workflow beta on the completed parity Stage 8A foundation:
inspect and find saved Objects, understand their software requirements without
probing them, compute and reuse Artifacts and CachedDatasets, and run complete ML
workflows with predictable local Method selection and selector/search-space
support for hyperparameterized repetition of layer groups.

The release version is `0.3.0b1`. This is a scoped beta milestone, not a promise
to complete the entire State Try 1 parity roadmap or stabilize every API for
`0.3.0`. This completed roadmap records the agreed release scope, seven
workstreams, dependency sequence, and release qualification gates. It is
requirements-only, not an implementation-ready plan or a claim that the new
capabilities are implemented. Focused plans settle the explicitly retained API,
format, and test-parameter decisions before code changes begin.

## Relationship To Parity Work

- Start after completed Stage 8A; retain its execution, managed lifecycle,
  runtime, reference, and Store contracts rather than reopening those systems.
- Expand the former Stage 10 application work into explicit Artifact,
  CachedDataset, Method-polish, and ML-integration milestones.
- Combine Object metadata and saved environment information into one
  record-sidecar, attachment, and query milestone. Reintroduce shared
  `dryml.records` mechanics for these concrete consumers; this supersedes the
  earlier roadmap decision to defer that package, not the current core identity
  or Store authority contracts. Do not restore the historical package wholesale.
- Remove legacy argument preparation/stripping hooks after metadata provides
  a separate home for non-construction information.
- Add selector/search-space list multipliers for repeated layer-group designs.
- Defer Stage 9 whole-pipeline implementation optimization and transformation.
- Retain relevant Stage 11 packaging, documentation, and release checks, without
  making every historical parity or cleanup item a beta prerequisite.
- Preserve the existing parity roadmap as historical context. This roadmap does
  not silently change its status or certify work beyond Stage 8A's recorded scope.

## Accepted Compatibility Boundary

There is no requirement to read or migrate pre-beta development Stores or
preserve the removed APIs for existing callers. Do not add legacy readers or
compatibility shims solely for those development versions. This permits a clean
format/API break; it does not authorize deleting or rewriting existing user data.

Stores written by `0.3.0b1` must remain accessible in later 0.3 releases through
direct compatibility or an explicit migration path. Establish versioned format
identification and retain representative beta fixtures so future changes can be
verified against that commitment. A future breaking format change must supply
and document its migration before shipping, not merely announce data loss.
This is a framework-owned persistence commitment, not automatic migration of
arbitrary subclass code or third-party payload formats. Document the supported
boundary and required author involvement. Python API stability is separate from
this persisted-data commitment.

## 1. Record Sidecars, Metadata, Environments, And Queries

**Combined outcome:** One focused plan owns reusable sidecar-record mechanics,
their Store serialization and attachment to references, and query integration.
User metadata and saved environment facts/requirements are its first concrete
consumers, replacing the formerly separate metadata and environment milestones.
Argument-hook removal follows this combined foundation.

**Ownership direction:** `dryml.records` collects reusable sidecar mechanisms;
core retains ObjectRef/StateRef identity, Repo attachment, Store publication,
and query authority. Environments retains its existing value schemas,
requirement declarations/collection, inspection, and compatibility semantics.
The focused plan settles narrow interfaces and import direction without making
records a second Object system or moving domain semantics into generic storage.
Reuse existing canonical codecs and locking rather than duplicating them.

**Shared query scope:** Treat environment information as typed queryable
metadata carried by records, so structural/reference predicates, user metadata,
and environment fields can participate in the same pre/post-filtering flows.
Queries inspect serialized sidecar authority without materializing Objects,
importing heavy dependencies, or launching environment probes. Matching a
recorded field is not itself proof of environment compatibility or admission.

**Attachment scope:** Provide mechanisms to attach, read, and update user
metadata on ObjectRefs and StateRefs, plus a save-time path associating captured
environment facts and declared requirements with the correct saved state.
Environment attachment here concerns serialization and Store association;
do not redesign the already settled environment declaration/collection APIs.
Common record mechanics need not impose identical mutability rules on every
record kind: editable annotations and historical environment evidence retain
their distinct meaning and domain validation.

### User Metadata

**Outcome:** Users can attach persistent metadata to both ObjectRefs and
StateRefs and use it to filter queries, with pre- and post-metadata filtering
analogous to the desired State Try 1 experience.

**Accepted attachment scope:** Support both targets. ObjectRef metadata describes
the object lineage; StateRef metadata describes one exact saved state. For
example, a project label can attach to an ObjectRef and an evaluation score to
a StateRef. The scopes are explicitly addressable and are not automatically
merged. A combined query view, if needed, is a separate design decision.

**Accepted mutability:** Metadata at both attachment scopes can be added or
edited without changing its target reference. In particular, StateRef metadata
can change after state publication without changing the StateRef or its
immutable payload. Sidecar annotation changes do not redefine the Object or
state they describe.

**Accepted flexibility:** Do not prescribe application-specific metadata fields
or a rigid domain schema. Names such as project, tags, and evaluation score are
examples, not required keys. Exact value types, encoding, limits, and query
operators remain focused-design questions; flexibility does not yet imply
support for persisting or querying arbitrary Python objects.

**Confirmed historical design starting point:** The project owner confirmed that
the parent workspace's
`docs/plans/2026-08-26-002-feat-state-aware-object-graphs-plan.md` is the earlier
metadata proposal they remember and liked. See Metadata requirements R29-R33a,
Queryable relations R37-R40, the MetadataValue sketch, and New Metadata And
Transfer Operations. It proposed user-defined string keys, nested scalar,
tuple, and mapping values, separate mutable sidecars, optimistic whole-record
replacement, and metadata-first or graph-first query composition. Its exact
limits and mutation API were still approval gate G3/Q7, not a shipped contract.
Use it as discussion input rather than automatically adopting its schema or
older CDef/node/occurrence attachment model; beta targets current ObjectRefs
and StateRefs.

**Scope:** Metadata sidecars using shared record mechanics, core Repo read/write
operations, query integration, and rebuildable acceleration where useful.
Metadata is separate from construction parameters and must not inadvertently
change CDef identity. The record abstraction does not prescribe application
metadata keys or erase the distinction between ObjectRef and StateRef scopes.

**Acceptance:** Metadata at both attachment scopes survives reopening a
Store and retains its exact target association; metadata predicates compose with
structural/reference queries; indexed and non-indexed execution agree; missing
or stale derived indexes cannot silently omit matching Objects.
Concurrent edits and interrupted publication have explicit conflict/recovery
behavior. Existing import-free query paths do not begin loading heavy Objects.

**Decisions for the focused discussion:**

- How do reads and queries explicitly select ObjectRef versus StateRef metadata?
  Is an optional combined view needed, and if so, what are its same-key rules?
- Which values are supported, and are updates replacement, merge, or patch?
- What metadata history or revision behavior is required for edits?
- What exactly do pre- and post-filter mean relative to structural matching,
  reference resolution, and materialization? Do not assume post-filter means
  executing arbitrary code on a loaded Object.
- What are missing-key, deletion, multi-Store precedence, and concurrent-update
  semantics? How much of the historical API is worth retaining?

### Saved Environment Facts And Requirements

**Outcome:** Saving Object state also captures the real saving environment and
the Object's declared environment requirements. An orchestrator can read both
from the Store alongside state information without materializing the Object,
importing its heavy dependencies, or launching a requirement-discovery probe.

**Scope:** Reuse the environment domain's records, requirement values, and codecs;
serialize and attach them through the shared sidecar mechanisms, with lightweight
inspection and queryable projections. Keep observed environment facts separate
from declared requirements: an installed package is not automatically a
requirement of every saved Object. Environment serialization is not conversion
into an unvalidated, arbitrary user-metadata dictionary.

**Acceptance:** A saved state exposes its associated environment facts
and requirements in a fresh lightweight process. A worker save describes the
worker, not the coordinator. Re-saving or copying an existing snapshot cannot
silently rewrite its historical evidence. Missing, conflicting, or incomplete
requirements are distinguishable from a known empty set. Publication failures
cannot associate evidence with the wrong Object or state.

**Decisions for the focused discussion:**

- Which declarations count: class, selected methods, referenced dependencies,
  or the full materialization closure? Preserve useful source attribution rather
  than silently flattening unrelated operation requirements.
- What is the association/publication model when unchanged Object state is
  saved from two different environments? Define save-time evidence separately
  from any claim about the environment that originally produced a payload.
- Which environment fields are persisted? Prefer software evidence without
  ambient environment variables, credentials, or unnecessary private paths.
- Does inspection only inform orchestration or also change load/admission
  behavior? Define absent/incomplete evidence under the new contract without
  requiring compatibility with pre-beta states.

No-probe inspection of saved declarations does not prove complete requirements
for arbitrary future operations. Destination admission remains separate, and a
save-time snapshot does not freeze an environment or solve live-code drift.

### Combined Acceptance And Design Questions

**Gate:** A fresh lightweight process can inspect and query attached user
metadata and saved environment information together with exact structural and
reference predicates. Indexed and non-indexed results agree; indexes remain
rebuildable from authoritative sidecars and Store contents. Tests cover mixed
record kinds, missing/unknown evidence, update conflicts, interrupted attachment
or save publication, and rebuilding without changing authoritative records.

The focused plan must settle record kind/version identification, attachment
cardinality and reference associations, domain payload validation, query field
projection and supported predicates, publication ordering, and multi-Store
behavior. User metadata remains flexible while environment values retain their
settled schemas. Shared serialization/query mechanics do not automatically
authorize editing or replacing historical environment evidence. No migration of
managed control records or unrelated sidecars into this layer is required merely
to introduce records for these two consumers.

## 2. Remove Legacy Argument Hooks

**Outcome:** Remove `__prepare_args__` and the argument-stripping hook from the
Object API and construction/definition paths. The requested `__strip_args__`
removal refers to the currently named `__strip_unique_args__` hook.

**Depends on:** The combined record-sidecar, attachment, and query milestone.
Its user-metadata capability removes the need for constructor injection and
subsequent identity stripping. This is a required beta API simplification,
not optional legacy cleanup.

**Scope:** Audit and remove hook definitions, overrides, callers, tests, and
documentation that require the old protocol. Reconcile the legacy Metadata and
UniqueID mixins with sidecar metadata and current ObjectId/reference semantics.
Do not replace the removed hooks with a renamed generic rewriting protocol.

**Baseline caveat:** Metadata is not the only current use. Torch and Keras
Sequential classes use `__prepare_args__` to normalize layer shorthands into
FactorySpec values; constructor signature handling invokes the hook, and
definition unique-argument stripping invokes `__strip_unique_args__`. Their
replacement or retirement must be explicit rather than assumed to follow from
metadata alone.

**Historical direction:** The August 26 State-Aware Object Graphs plan already
recorded hook removal in KD13-KD14: move shorthand normalization into
canonicalization, remove UniqueID/Metadata mixins and stripping hooks, and keep
categorical projections hook-free without rewriting legacy fields. Reconcile
that direction with today's signature/canonicalization boundaries before
choosing a replacement; do not treat retaining shorthands as an unexplored idea.

**Acceptance:** Normal construction, definition-only orchestration,
querying, and exact state restoration work without either hook. Metadata no
longer needs constructor injection or identity stripping. Retained layer
authoring APIs have documented normalization behavior; removed shorthand forms
have clear migration guidance. Tests cover constructor binding, defaults,
identity, reference topology, and loading without replaying removed hooks.

**Decisions for the focused discussion:** Which mixin behaviors remain useful;
whether layer shorthands become explicit factories or are retired in favor of
FactorySpec inputs. Pre-beta definitions containing legacy metadata/uid arguments
do not require a reader or migration path. Define actionable rejection where
incompatible data is encountered, without silently rewriting its identity or
adding legacy shims.

## 3. Artifacts API Revision

**Outcome:** Align Artifact authoring and use with the project owner's vision,
including managed `.compute` and subclass-declared references for heavy
dependencies.

**Scope:** Review the current API before extending it. Establish the abstract
authoring contract for computation and payload persistence, leaving domain
inputs and reuse behavior to subclasses and their users.
Use the existing managed lifecycle rather than a second compute/checkpoint state
machine. Keep large computed payloads in Object state, not CDef parameters.

**Accepted authoring model:** The top-level Artifact leaves `.compute` and
related subclass responsibilities abstract. The trusted class author defines
the constructor and implements those methods, chooses where input references
are stored, and explicitly materializes the references needed by computation.
Artifact does not discover heavy inputs, prescribe their attribute layout, or
automatically resolve them through a new dependency-declaration protocol.
The managed lifecycle supplies operation controls, not the subclass's domain
logic. Exact abstract method signatures and managed integration remain API
review details, not a reason to introduce automatic input handling.

**Accepted API boundary:** Artifact is an abstract API shape, not a framework
cache/reuse policy. Authors and users define their subclasses and domain
behavior, including any result reuse or input-freshness policy they want.
Do not add automatic Artifact discovery, memoization, cache invalidation, or a
mandatory reuse protocol. The base composes existing managed and persistence
contracts; supplied subclasses document their own behavior.

**Accepted heavy-input contract:** Artifact subclasses declare heavy inputs,
such as models and datasets, as references rather than materializing Object
dependencies. The author's `.compute` implementation materializes the references
it needs in its execution context to perform the computation. Materializing a
saved Artifact restores its computed payload while leaving its reference inputs
unmaterialized; it neither recomputes the result nor loads those inputs merely
to expose the result.
Compute-time materialization must not turn those reference inputs into persisted
materializing edges. Software-environment requirements remain a separate concern
from these references to heavy input Objects.

**Acceptance:** A representative custom subclass declares heavy inputs
without loading them in an orchestrator, computes directly and through supported
execution paths, publishes an exact saved result, and restores it without
recomputing or materializing its reference inputs. Tests verify both sides of
the boundary: computation materializes required inputs, while loading the saved
metric in the orchestrator does not. Failures and interrupted computation are
not reported as complete; resume is offered only where the subclass supports it.
These checks qualify DRYML's supplied subclasses and acceptance examples; they
are not a promise to infer or enforce correct behavior in arbitrary author code.

**Decisions for the focused discussion:**

- What does a minimal user-authored subclass look like, including `.compute`
  arguments, return value, payload access, and managed controls?
- For supplied subclasses and examples, choose appropriate reference forms and
  document explicit loading, exact-state selection, and missing-input failures.
  These are author-owned choices using existing core APIs, not a universal
  Artifact input schema. Reference-as-value edges are not automatically saved
  as owned dependencies.
- Document supplied subclass behavior for repeated computation and uncomputed
  payload access within existing managed invocation rules. CachedDataset owns
  its concrete cache behavior; this does not impose a universal Artifact reuse
  or freshness policy on user subclasses.

## 4. CachedDatasets With NumPy And Parquet

**Outcome:** Materialize and reuse datasets through NumPy and Parquet codecs,
with CachedDataset conforming to the revised Artifacts API.

**Accepted base shape:** CachedDataset inherits both Artifact and Dataset. It
has an explicit computation phase; once computed, it supports ordinary Dataset
iteration over the cached result. This composes the Artifact compute API with
the Dataset consumption API rather than introducing a separate cache manager.
Before successful computation, it does not expose an iterable completed cache;
the precise not-computed error belongs to the focused API plan. Iteration is
not an implicit request to compute. Loading a saved computed CachedDataset
restores its iterable result without rerunning the source pipeline or
materializing reference inputs solely to iterate the cached payload.

**Scope:** Dataset-to-cache computation, codec selection, payload manifests,
iteration, saved-state restoration, and compatibility with data/Method specs.
Use ordinary immutable Object-state publication rather than the retired mutable
Store-root cache protocol. Keep Parquet dependencies optional and lazy.

**Acceptance:** Both codecs round-trip their declared supported data
shapes, dtypes, structure, ordering, and cardinality; restored caches are
re-iterable without rerunning the source pipeline. Empty inputs, unsupported
data, partial writes, and corrupt payloads produce defined outcomes. Cache
creation and consumption work through the revised Artifact lifecycle.
Exercise the not-computed, successfully computed, and restored-computed states,
including ordinary Dataset composition after computation. Interrupted or failed
computation must not expose a partial cache as a completed iterable dataset.

**Decisions for the focused discussion:** NumPy tensor/tree support versus
Parquet tabular/nested support; schema and null handling; chunking and bounded
memory; whether memory mapping is needed for beta; source identity and exact
cache reuse; and whether partial-cache resume is required or explicitly absent.
The two codecs need not support identical data structures, but must not silently
coerce unsupported inputs.

## 5. Method Selection Polish

**Outcome:** Greedy, local implementation selection works predictably for
individual Methods and the data/model compositions used in beta workflows.

**Baseline:** Current Methods already select a uniquely most-specific compatible
implementation. Map, Pipe, Project, and AutoEncoder perform local selection from
threaded specs. This work is validation, ergonomics, and targeted corrections,
not a new selection system by default.

**Acceptance:** Backend and batching traits select the intended local
implementation; missing traits, incompatible candidates, and ties have useful
errors; composed data/model paths retain correct output specs; cached calls
reject incompatible inputs. Candidate selection does not execute candidates to
guess their behavior or import unrelated frameworks.

**Decision for the focused discussion:** Confirm whether "greedy" means the
current most-specific-compatible rule or a different local preference policy.
Do not introduce cost ranking, automatic representation conversions, graph-wide
optimization, fusion, or generated implementations without a separate decision.

## 6. Selector And Search-Space List Multipliers

**Outcome:** Extend selector and search-space hyperparameter support to list
multipliers, allowing users to define an arbitrary ordered sequence of layers
as a group and stack that group a selected number of times.

**Accepted scope:** Repetition count is part of the selector/search-space model,
not merely manual Python list multiplication before constructing a definition.
This is a required beta feature. It does not introduce global Method pipeline
optimization or an automatic architecture-search scheduler.

**Provisional breadth:** Target layer lists for beta, rather than requiring a
general-purpose sequence algebra. The project owner may refine this boundary
during the focused plan.

**Accepted linked-value semantics:** For beta, each hyperparameter in a repeated
group has one selected value shared by the corresponding positions in all
copies. Sampling chooses each group parameter once per generated architecture;
grid enumeration varies those group-level choices, not independent choices for
each repetition. Selector matching must preserve the same cross-copy linkage.
Independent per-copy hyperparameters are deferred to a possible future extension.
Repeated layer groups construct independent layer instances with linked
configuration values, not tied weights. Sharing must be explicitly expressed;
it is not an implicit effect of repetition or equal hyperparameter values.

**Design context:** The project owner recalls an earlier plan for this feature;
the specific plan has not yet been located in workspace documents or reachable
parent/child documentation history. Related bound-definition and state-aware
graph plans describe partial Selector/SearchSpace expressions and layer
normalization, but do not settle repetition semantics. Do not treat those as
the recalled multiplier plan or invent previously accepted decisions.

**Acceptance:** A layer-group template with a variable repetition count
can produce valid concrete architectures through search-space sampling and
finite grid enumeration. Corresponding selectors match supported repeated
structures consistently, including the support selector for generated cases.
Concrete outputs preserve layer ordering, linked parameter values, and intended
object sharing/independence; round-trip persistence retains their meaning.
Tests distinguish matching linked repetitions from sequences with conflicting
values at corresponding positions across copies. Exercise representative
TensorFlow and PyTorch layer groups without restoring removed
argument hooks or importing frameworks during lightweight selector queries.

**Decisions for the focused discussion:**

- Locate the earlier design if possible, then settle public expression syntax
  and refine the provisional layer-list boundary.
- Define zero/invalid counts, finite count ranges, nested groups, and expansion
  bounds without accidentally introducing unbounded grid materialization.
- Preserve the accepted independent-layer behavior in canonicalization and
  construction, without accidental Python list aliasing. Explicit sharing uses
  the applicable existing graph contracts, not a new implicit weight-tying mode.
- Define selector matching, concrete canonicalization/identity, portable
  encoding, and equality with explicitly expanded sequences.

**Dependencies:** Align with argument-hook removal and the current
signature/canonicalization boundaries. Integrate before final ML qualification;
use focused repetition tests rather than adding a full hyperparameter sweep to
every training-matrix case.

## 7. Full ML Workflow Integration And Polish

**Outcome:** The parts form a practical end-to-end user experience rather than
only passing isolated subsystem tests.

The project owner selected two independent acceptance axes: ML workload and
execution circumstance. Every workload must work under every circumstance.
Metrics must be computed in Artifacts after training in all cases, not replaced
by training-history values or ad hoc scalar calculations outside Artifacts.

Both TensorFlow and PyTorch model implementations are required for every
workload and circumstance. For the initial PyTorch workflows, use the dataset's
NumPy representation to simplify integration; native Torch dataset delivery is
not an additional beta prerequisite. Both MNIST workloads use TFDS as the source
in both framework variants, with NumPy delivery for the PyTorch paths.

### Accepted Workloads

| ID | Workload | Training | Post-training metric Artifact |
| --- | --- | --- | --- |
| W1 | Small MNIST classifier using a TFDS source dataset | One epoch | Categorical accuracy on the test dataset |
| W2 | Small MNIST autoencoder using a TFDS source dataset | One epoch | Reconstruction loss on the test dataset |
| W3 | Random samples from an underlying polynomial truth plus Gaussian error; simple neural-network regressor | Budget to be selected | OLS loss on the persisted CachedDataset test set |

For W3, generate, build, and persist the test CachedDataset as a separate initial
step, before the matrix runs. Reuse that exact saved test dataset for every W3
matrix run, including repeat runs against that fixture; do not resample or
rebuild it in each case. Retain its StateRef and verify reuse. Training data is
separate from the cached test data. Codec coverage must not silently turn a
shared test fixture into different random datasets.

Generate the test samples once and persist equivalent NumPy and Parquet caches.
Verify round-trip equivalence for this shared supported dataset. Use NumPy for
the full training/execution matrix and reuse its exact saved cache across both
frameworks and all execution paths; Parquet does not need another full matrix.
Distinct codec caches need not share a StateRef, but must contain the same test
samples.

### Accepted Execution Circumstances

| ID | Circumstance | Required behavior |
| --- | --- | --- |
| C1 | In-process, non-managed session | Train and evaluate locally in ordinary Python session mode, without a worker launch |
| C2 | Managed session, no worker launch | Train and evaluate in the current process under session-managed controls |
| C3 | Orchestrated worker training and evaluation | Train and compute metric Artifacts in workers; the orchestrator uses a scoped exception only to materialize saved metric Artifacts and compare their values with expected results |

Here "managed session" means session/runtime resource controls, not the
`dryml.managed` operation lifecycle. C1 does not require bypassing managed
`.compute` or training lifecycle APIs. In C3, both training and post-training
metric Artifact `.compute` execute in workers. The orchestrator receives exact
saved metric references and materializes only those computed results for
assertions; it does not recompute metrics or materialize the trained model or
test dataset. Artifact dependency references must support loading a computed
metric payload without materializing its heavy inputs.

### Required Matrix

| Workload | C1: Python in-process | C2: Managed in-process | C3: Local subprocess | C3: Same-host Ray |
| --- | --- | --- | --- | --- |
| W1: MNIST classifier | TF + Torch | TF + Torch | TF + Torch | TF + Torch |
| W2: MNIST autoencoder | TF + Torch | TF + Torch | TF + Torch | TF + Torch |
| W3: Polynomial regression | TF + Torch | TF + Torch | TF + Torch | TF + Torch |

All entries are required: three workloads times two model frameworks times four
execution paths gives 24 acceptance runs. Both local subprocess and same-host
Ray must execute every C3 workload/framework combination. The full matrix runs
on CPU; targeted GPU qualification is additional rather than a second complete
matrix. Keep process-global session/framework initialization isolated between
cases; changing modes after
importing a heavy framework is not assumed safe. In C3, the materialization
exception is scoped: ordinary orchestration remains definition/reference-only
outside it, including
after an assertion or loading failure.

The exported `dryml.runtime.materialization_scope(...)` provides an existing
generic override, with maintained scope/admission tests. It is not a
metric-specific permit and does not yet establish this complete workflow.
Verify and document the supported explicit metric-loading path rather than
assuming the scope makes ordinary constructors or execution-result recovery
automatically return live Objects. Do not present the override as undoing
framework initialization or runtime visibility controls.

**Acceptance:** Selected workflows demonstrate correct results,
practical performance, environment inspection without Object probing, exact
state reuse, and honest recovery behavior. Exercise direct local use and the
supported local-subprocess and same-host Ray paths. Test checkpoint/resume only
where the method/framework declares that capability. Update tutorials, examples,
errors, and API docs to match the verified workflows.

### Accepted Recovery And GPU Gates

Add one representative real ML interruption/checkpoint/resume workflow as a
beta release gate. Use a training implementation with declared recovery support,
interrupt after a valid checkpoint, resume, complete training, and compute its
metric Artifact. Verify retained progress and valid final state rather than
silently restarting training or treating partial work as completion. Select the
specific workload/framework/execution path in the focused plan; do not multiply
all 24 successful-path runs by this scenario.

Run targeted TensorFlow and PyTorch GPU qualification in addition to the CPU
matrix, checking actual device use and relevant runtime controls rather than
accepting silent CPU fallback. The hardware and execution-path selection remain
qualification-plan details. GPU checks may run on an approved local host or
self-hosted runner; availability on standard GitHub-hosted runners is not assumed.
GitHub also offers billed GPU-capable larger runners, but configuring or buying
that infrastructure is not authorized by this roadmap. Record GPU evidence and
any unrun coverage honestly rather than treating a skipped test as qualification.

### Remaining Acceptance Decisions

- Select small architectures, preprocessing, batch sizes, and the W3 training
  budget for the accepted TensorFlow/PyTorch coverage.
- Define the autoencoder loss and whether W3's OLS metric means sum or mean of
  squared residuals, evaluated against noisy observations or polynomial truth.
- Set seeds, polynomial coefficients, sampling domain, Gaussian noise scale,
  dataset sizes, numerical thresholds/tolerances, and runtime/memory budgets.
  Do not require bitwise-equal training outcomes across execution circumstances.
- Define explicit fixture creation/reuse and cleanup ownership; NumPy
  full-matrix coverage and dual-codec round-trip coverage are settled.
- Prepare TFDS data explicitly for real integration runs; routine tests must
  not silently download MNIST. Keep heavyweight/network validation opt-in.
- Select the representative recovery case and targeted GPU checks/hardware.
  Do not multiply all 24 runs by every failure scenario or additional frameworks.

## Delivery Sequence

The table records ownership and dependency gates, not parallel implementation
authorization. Workstream numbers identify scope; the steps below describe the
delivery order, including early workflow design.

| Workstream | Owning area | Dependency gate |

   user metadata and serialized save-time environment facts and requirements.

   non-metadata uses before polishing higher-level APIs.

   argument-hook removal and concrete layer normalization.

Each workstream needs a focused API and persistence discussion before its
implementation plan. Implementation remains serial in this workspace. Workflow
validation is ongoing, not postponed entirely to the last step.

## Focused-Plan Handoff

The open questions within each workstream are deliberate inputs to its focused
plan, not missing release-feature decisions. Resolve them before implementing
the affected contract; do not silently expand scope while answering them.
Each focused plan should specify its public API changes, persisted formats and
failure behavior where applicable, verification evidence, and documentation.
The provisional layer-list boundary may be refined there as explicitly agreed.
Locating the historical multiplier plan is useful context, not a release gate.

No implementation, package publication, paid runner provisioning, or broader
parity work is represented as completed or authorized merely by finalizing this
roadmap. The local Markdown remains the canonical roadmap; a Proof publication
is a review/share copy, not an automatic two-way synchronization.

  declared support matrix. Heavy/network integration remains explicitly opt-in.
- All 24 workload/framework/execution runs have recorded acceptance results,
  with metric thresholds, shared W3 full-matrix test-cache identity, and
  NumPy/Parquet round-trip equivalence evidence. Subsystem-only tests are not
  substitutes. Private datasets, credentials, and outputs stay out of source
  control.
- The representative real ML interruption/resume gate and targeted TensorFlow
  and PyTorch GPU qualification have recorded results, separate from the CPU
  matrix. Unrun checks require an explicit release disposition, not an implied
  pass.
- Document the clean break from pre-beta Stores and the forward migration
  commitment for `0.3.0b1` framework-owned persistence. Version identifiers and
  representative fixtures support that commitment; release notes distinguish
  persistence guarantees from API stability and author-owned payload behavior.
- Critical/high-priority findings are resolved or explicitly dispositioned by
  the project owner under workspace policy. Deferred items are not called fixed.
- Package metadata uses `0.3.0b1`, installation instructions show prerelease
  opt-in, and optional dependencies remain optional. Publishing to PyPI is a
  separate explicitly authorized action, not part of writing this roadmap.

## Deferred Scope

Whole-pipeline Method optimization/transformation; a universal product/provenance
ontology or wholesale restoration of the historical records package; automatic
environment provisioning; multi-host/non-shared-Store
execution; hot reload and live-Object migration; and historical parity work
not needed by the agreed beta workflows remain outside this milestone.
